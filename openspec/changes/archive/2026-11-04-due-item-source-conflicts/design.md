# Design

## Context

现状（详见 proposal.md「Why」）：`bb-sync due` 走两条独立路径——课程主页 To Do 模块（结构化，日期权威）和公告解析（文本推断，名称权威）——最后在 `merge_due_items()` 里以「To Do 优先、公告重复条目丢弃」的单赢家方式合并，然后由 `build_due_markdown()` 渲染 `due.md`。

约束：

- `DueItem` 是 `frozen=True` 的 dataclass，合并只能通过替换产生新对象。
- `due.md` 的 `- [x]` 完成状态靠 `_item_signature()`（日期 + 课程 + 标题）从上一版文件里认回。
- `bb-sync due` 目前只访问两个页面：课程主页与公告页；`Assignments and Exams` 页面只在 `run` 时抓文件。
- 现有测试 `tests/test_units.py` 已固定了公告解析、合并优先级、渲染与勾选的契约。

## Goals / Non-Goals

**Goals:**

- 公告里无编号的作业名能被识别，不漏收。
- To Do 与公告对同一件事的叫法不一致时，两个叫法都保留，并在 `due.md` 里显式标注。
- 分歧在终端与 `--json` 输出里可观测。
- 新增规则用真实公告文本做回归夹具。

**Non-Goals:**

- 不抓取 `Assignments and Exams` 页的附件名去反推正确编号（多一次页面访问、且是另一种证据来源，留给后续）。
- 不自动「纠正」Blackboard 的错误命名：只呈现分歧，不替教务改标签。
- 不改公告页的抓取方式与登录流程。

## Decisions

### D1：别名挂在 `DueItem` 上，而不是另建冲突实体

在 `DueItem` 增加 `aliases: tuple[str, ...] = ()`（frozen dataclass 默认空元组），合并时用 `dataclasses.replace()` 把公告标题写进 To Do 条目。

- 放弃的方案：新建 `Conflict(first, second)` 实体并让清单同时容纳普通条目与冲突条目。收益是信息更全，但会污染排序、分组、渲染和勾选签名四处，且 `due.md` 的定位是给人看的一条行，不是数据库。
- 放弃的方案：把两个标题拼成 `Assignment 5 / Homework assignment 4`。它无法区分「分歧」与「同一件事的两种正常写法」，也无法让读者知道哪个来自公告。

### D2：分歧判定归一化为「编号 + 主题词集合」

对两个标题各抽 `(编号, 主题词)`：编号来自标题里 1–2 位的阿拉伯数字；主题词复用现有
`_title_tokens()` 的停用词与纯数字过滤。「是不是同一件事」和「叫法有没有分歧」分两步：

1. **同一事件判定**（`_same_event`）先看「同课程 + 同日期」，再满足任一条件即可：双方都是
   作业类说法且编号相同、主题词有交集、或中文标题互相包含。补上「同编号作业」这条是因为
   仅靠主题词交集，`HW4` 与 `Homework assignment 4` 的词集合（`{hw}` vs
   `{homework, assignment}`）没有交集，同一天会被当成两件事重复列出。
2. **分歧判定**（`_titles_conflict`）只在已判定为同一事件后运行：

| 条件 | 结论 |
|---|---|
| 双方都有编号且不同 | 分歧 |
| 双方编号相同 | 无分歧（措辞差异） |
| 一方无编号、主题词有交集 | 无分歧 |
| 双方都无编号且主题词无交集 | 判不成同一事件，两条都保留，不做猜测性合并 |

- 放弃的方案：字符串相似度（`SequenceMatcher`）阈值。`Assignment 5` 与 `Homework assignment 4` 相似度高，正好会把该报的分歧判成重复；而 `HW4` 与 `Homework assignment 4` 相似度低，会把正常的措辞差异判成分歧——方向完全相反。
- 放弃的方案：只比较原始字符串是否相等。`HW4` vs `Homework assignment 4` 会被误标为分歧。

### D3：渲染把别名放在标题后的全角括号里

`- [ ] **2026-11-13**（还有 9 天） — [DDA5002](…) — Assignment 5（公告称 Homework assignment 4）`

`due.md` 头部增加一行说明括号含义。别名经 `_escape_markdown()` 处理，避免公告标题里的 `*`、`[` 破坏行结构。

### D4：勾选签名只含基础标题，不含别名

`_item_signature()` 保持「日期 + 课程 + 基础标题」。别名变化（公告被删除、措辞被修改）不改变签名，已完成状态不会复位。

已知牺牲：若某次同步后 To Do 条目消失、只剩公告条目，基础标题会从 `Assignment 5` 变成 `Homework assignment 4`，该条的勾选状态会复位。这属于来源本身消失导致的对象身份变化，接受。

### D5：放宽作业名识别，但把守卫移到「语境」而非「编号」

`_ASSIGNMENT_NAME_RE` 改为「作业词 + 可选编号 + 可选主题」，并保留「标题或上一行必须含作业词」的语境守卫。截止行仍需同时含日期与截止词，这条不变。

- 放弃的方案：继续要求编号，仅对特定课程硬编码例外。不可维护。
- 放弃的方案：完全取消名字要求，只看到日期就收。会把「材料上传通知里提到的日期」等大量噪音带进待办。

### D6：分歧可观测用最轻的方式

`service` 层在汇总里输出分歧条数；`DueItem.as_dict()` 增加 `aliases` 字段（空列表也不省略，保持结构稳定）。不新增命令行开关。

## Risks / Trade-offs

- [放宽识别后误收无编号的普通提醒] → 保留「相邻行含作业词 + 截止词 + 日期」三重门；用现状测试里的反例（`Week 4 Materials Uploaded`）作回归夹具，并补充「标题含 homework 但日期指别的事」的用例。
- [`due.md` 行变长、表格类截图不好看] → 只在实质分歧时出现，且头部有说明；接受。
- [`as_dict()` 新增字段可能影响下游脚本] → 只增不减；在 CHANGELOG 标 BREAKING 并给出版本号提升（2.3.0）。
- [编号归一化对中文作业名（「作业 5」「第五次作业」）覆盖不足] → 本次只处理阿拉伯数字；中文写法先不推断分歧，避免误报；记入 Open Questions。
- [公告页结构变化导致别名来源缺失] → 别名缺失时退化为现状行为，不影响主流程。

## Migration Plan

1. 改动落在 bb-sync，版本按 minor 提升（2.2.1 → 2.3.0），CHANGELOG 记录 `due.md` 行格式与 JSON 字段的 BREAKING 变化。
2. 用户重跑 `bb-sync due` 即可得到新格式；`due.md` 是生成物，无需数据迁移。
3. 回滚：恢复旧版本后重跑 `bb-sync due`，别名消失、签名不变，已完成状态保留。

## Open Questions

- 是否把 `Assignments and Exams` 页的附件名（如 `DDA5002HW4_Fall26.pdf`）作为第三方证据，用于自动判定哪一方的编号更可信。
- 中文作业命名（「第五次作业」）的归一化是否需要纳入分歧判定。
